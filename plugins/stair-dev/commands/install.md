You are setting up Stair, this plugin, for the person: it keeps a record of their Claude Code sessions in an account of theirs. The person sees three short steps; the reading behind them is yours. Do them in order, skip none, and do not run setup before they say yes.

The plugin's directory is `${CLAUDE_PLUGIN_ROOT}`. If that is not an absolute path, use the newest directory under `~/.claude/plugins/cache/stair-ai/stair/` (for `/stair-dev:install`: `~/.claude/plugins/cache/stair-ai-dev/stair-dev/`).

This plugin's name is the `name` in `.claude-plugin/plugin.json` there: `stair`, the release channel, or `stair-dev`, the staging channel, which writes to the staging ledger and installs side by side with `stair`. The steps below are written for `stair`; for `stair-dev`, the state directory is `~/.stair-dev` and the command `stair-dev`.

First see whether this is a reinstall: run `ls ~/.stair` (it needs nothing installed). If it lists `owner.key`, this machine still has the keys of an earlier install (an uninstall leaves them), and setup reconnects that account, with its records and the machine's name; no invite code is needed. Otherwise ask once whether they have used Stair before and kept their keys (`owner.key` and `master.key`, or a copy of their `~/.stair` folder). If they did, ask only where the folder is, never for what is in the files (keys must not be pasted into the chat), and use `--restore FOLDER` in step 3.

1. **Read the code, then say three lines.** Read all of `bin/stair`, `hooks/hooks.json`, `rl_plugin.py`, `mapper.py` and `PRIVACY.md` in the plugin directory, and note the version (`version` in `.claude-plugin/plugin.json`). Then tell the person three lines and no more: what it reads (the transcripts Claude Code writes, nothing else of theirs); where it sends data (only the ledger named in `channel.env`; besides, GitHub, for a public notices file at most hourly and to build its Python environment); and whether you found anything wrong. If anything sends data elsewhere, hides what it does or looks malicious, say so in full instead, and stop. If they ask for details, give them.

2. **Show the notice in short, and ask.** Show this, exactly as written, with nothing added, left out or reworded (translate it faithfully if they write in another language): the line "Nothing has been sent yet.", then the whole "In short" section of `PRIVACY.md`, then the line "The full notice is PRIVACY.md (version `2026-10-31`); ask me anything about it." Then ask one question with AskUserQuestion, "Start recording from your next session?", with the options "Yes, start" and "No, not now", neither marked as recommended; without AskUserQuestion, ask in the message and wait. Answer their questions from `PRIVACY.md`, plainly and briefly. If they want to see what would be sent, run `"${CLAUDE_PLUGIN_ROOT}/bin/stair" rl preview` and show its output: the last turn of this session as the ledger would get it, sent nowhere (the first run builds the plugin's Python environment, about a minute). Without a clear yes, stop: nothing is installed further and nothing has been sent.

3. **Set up, then say two lines.** Check the version again: if it is not the one you read (Claude Code can update a plugin meanwhile), read what changed (`CHANGES.md` and the files above) and tell them before going on. Then run the line that fits, with the invite code from the argument (`$ARGUMENTS`) or, for a new account without one, ask for it:

   ```
   "${CLAUDE_PLUGIN_ROOT}/bin/stair" rl setup --invite CODE --accept-privacy-notice 2026-10-31   # a new account
   "${CLAUDE_PLUGIN_ROOT}/bin/stair" rl setup --accept-privacy-notice 2026-10-31                 # the keys are still here
   "${CLAUDE_PLUGIN_ROOT}/bin/stair" rl setup --restore FOLDER --accept-privacy-notice 2026-10-31 # the keys were kept in FOLDER
   ```

   A new account names this machine after its kind (`claude-code-mac`, say); add `--agent-name NAME` only if they ask for another name, which is readable on the ledger. A reconnected account keeps the machine's earlier name. Setup builds the plugin's Python environment (with `uv` or Python 3.12+; `curl -LsSf https://astral.sh/uv/install.sh | sh` installs uv), creates the account or reconnects it, makes the keys and sends one test record. If it fails, show the error and stop; do not retry with other values on your own. Two failures leave them a choice, which is theirs: when setup says the master key is not on this machine, or opens none of the sessions, explain that earlier records can be read only with the key they were recorded with; if they have it, use `--restore` with its folder; only if they say it is lost, run setup again with `--new-master-key`, those records then staying unreadable. When it says another key is already here, `--force` uses the kept one and moves the other aside, deleting nothing; ask before adding it.

   When it succeeds, say two lines. First: the account is made, or reconnected (with `readable_with_this_key` of `sessions_on_ledger` earlier sessions readable), and a test record was sent; recording starts with their next session. Second, as written: "Your two key files, `~/.stair/owner.key` and `~/.stair/master.key`, are your account: keep a copy somewhere safe; without them your records can't be read." Then offer to add the `stair` command to their own terminal (`"${CLAUDE_PLUGIN_ROOT}/bin/stair" link` writes `~/.local/bin/stair`, a small script that runs the installed version; `stair-dev` for the staging channel). If they named projects to leave out, run `"${CLAUDE_PLUGIN_ROOT}/bin/stair" rl exclude FOLDER` for each.

Everything else they may ask about is in `PRIVACY.md` and `README.md`: viewing their records (`stair rl viewer`), leaving a project out (`stair rl exclude`), attaching an e-mail (`stair rl claim`), stopping (uninstall).
